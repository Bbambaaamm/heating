## Observed incident and limitations

- 2026-10-08 around 21:56: the Flow V4 state machine entered
  EMERGENCY_COOLING, then switched to RESTORING after about 30 s without
  renewed confirmation of two flow paths; it ended in HARD_LOCKOUT.
- 2026-10-09 around 12:31: a supervised live state-machine validation
  confirmed motor movement of two valves; flow paths were accepted;
  V4 returned to NORMAL and the boiler was enabled.
- Around 12:35: boiler relay and flame were on. Control start was initially
  repeatedly cancelled by attribute-only updates to
  `binary_sensor.kotel_should_be_on`. A live trigger fix was installed.
- Around 12:48: EMS reported **2964 (insufficient heat-exchanger flow)**.
  V4 opened relief valves, stopped the boiler and initiated recovery.
  This is a *genuine fault report*, not proof of a spurious lockout.
- `sensor.boiler_pc0flow` reported 0 L/h even with flame and circulation
  pump active. Treat it as **unverified for safety decisions** until the
  sensor's support and real physical meaning are confirmed.

Software validation does not establish actual hydraulic flow. Only physically
verified pressure, pump operation, open manual/radiator valves and an adequate
water path (or a professionally assessed bypass/balance) can resolve a genuine
2964 flow restriction. Manufacturer diagnostic codes 2964–2967 remain guarded.

## Live changes made via Home Assistant config API

1. V4 boiler start: `binary_sensor.kotel_should_be_on` triggers now use
   explicit OFF→ON and ON→OFF state boundaries. Attribute-only PI / zone-count
   reports no longer restart the 120-second start delay.
2. Flow V4: if heatblock drops below 60 °C and the flame is off,
   EMERGENCY_COOLING transitions to RESTORING only after **two flow paths
   were confirmed** or the **full 120-second path-verification window** timed
   out. At timeout without flow proof the lockout remains latched,
   so restore cannot enable the boiler.
3. Boiler watchdog: warns at heatblock above 69 °C, HARD_LOCKOUT, long relay
   OFF with active demand, cold-without-flame during demand, and loss of EMS.
   HA persistent notifications use stable IDs. Phone push is only sent for
   new relevant trigger events. Watchdog never controls any actuator.
4. An independent ChatGPT hourly condition watch was configured, separate
   from the Git repository and the HA per-event watchdog.

## Automatic regression checks

`tests/test_boiler_v4_live_recovery_snapshot.py` asserts:
- no early restoration when paths are still unverified;
- hard timeout and existing fault guards are preserved;
- controller turns relay OFF before emergency valve opening;
- start delay and both pre-/post-delay policy gates remain;
- watchdog cannot switch relays;
- both YAML fallback relays ignore attribute-only demand reports.

The test checks a static state-machine snapshot and does not simulate
physical pump flow, gas firing, sensor update timing or thermal dynamics.
Full HA runtime/hardware verification must be performed during controlled,
observed heating cycles; **do not manufacture a 2964 fault** for testing.

## Operational acceptance criteria

- Flow V4 stays in NORMAL during ordinary heating.
- Required zones satisfy target/PI, relay ON and burner/pump follow demand.
- Flow V4 can safely return all eight TRVs to scheduled/manually valid
  targets and master enable on fault clearance.
- On a real 2964/2965/2966/2967, shutoff remains immediate and fault recovery
  cannot re-enable an unverified flow path.
- A measured lack of adequate hydraulic flow must escalate as a fault;
  software should not silently bypass lockout.
- Before any future Git → HA promotion, compare the latest HA config hashes
  and update the snapshot; duplicate controllers must not be introduced.

## Reversal
Restore only the touched live automations from the preceding HA backup or
verified previous configuration, preserving the existing object IDs.
The previous V4 cooling gate was only: heatblock <60 and flame OFF; restoring
that old condition reintroduces the original early-recovery race and is not
recommended. For the watchdog, disable the new UI automation if necessary.
Reverting the Git branch alone **does not roll back HA changes**.
